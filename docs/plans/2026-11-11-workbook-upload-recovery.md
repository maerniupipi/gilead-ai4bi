# 大文件上传状态修复

现场证据：生产日志显示上传 201、无进程重启，Gilead005 的 100,000 行文件完整保存；同一 XLSX 在服务器解析耗时 32.7 秒。前端对上传连接的网络错误直接显示 Failed to fetch，之后刷新列表却看到了已保存文件。

方案：增加后台上传接口，先持久化接收文件并迅速返回任务标识，再串行解析，避免占用主事件循环及并发解析耗尽内存。状态按账号隔离；请求标识和内容指纹保证重试不重复入库；工作簿和成功状态原子提交。启动时恢复中断状态，重新打开页面后继续处理和查询。保留旧上传接口并在线程中运行。

前端：显示传输、排队、解析和连接恢复状态；网络中断时先查询相同任务，必要时以相同标识重试，刷新页面可恢复在处理的文件。成功后合并工作簿并刷新列表，不保留误报失败。

验证：覆盖响应丢失、轮询断线、账号切换、并发重试、配额预留、跨账号访问、解析失败和重启恢复。用原 9.3 MiB / 20 列 / 100,000 行文件在服务器测试，确认解析期间其他请求仍可响应，部署时保留五个账号所有现有数据。
